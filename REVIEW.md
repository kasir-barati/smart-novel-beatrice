## Summary

This range (`1b420bd..0eaef74`) builds the full TTS Generation feature — provider abstraction (step 1), `audioVoices` (step 2), `generateAudio` accept/validate/publish (step 3), worker consume/synthesize (step 4), worker upload/completion (step 5), retry & DLQ (step 6), observability/logging (step 7) — plus an out-of-band SSRF fix (`8e884d9`). Each step is scoped, tested at the tier `.github/CONTRIBUTING.md` calls for, and committed individually with a matching `docs: self-improvement pass` commit. Overall this needs changes: the implementation is solid and the SSRF fix is applied consistently to both outbound callback URLs, but there's a real retry-classification gap in `upload_job` (a re-validation failure is treated as infinitely retryable instead of going straight to the DLQ) and the "stream to a temp file" AC from step 4 isn't actually implemented as streaming.

## Findings -- FIX THEM ALL

1. `src/modules/audio/worker.py:206` (`upload_job`) — A `genUploadUrl` that fails the allow-list re-validation raises `CallbackUrlNotAllowedError` uncaught, unlike `_post_status_update` (`worker.py:59-66`), which catches the same exception and treats it as a no-op. In `handle_message`, this exception is caught generically (`worker.py:442`) and passed to `decide_retry` (`retry.py:17`), whose `_status_code_of` (`retry.py:50-57`) returns `None` for anything without a `status_code` attribute — the same branch used for genuine network errors — so it's classified as **always retryable** (`retry.py:34-35`). A URL that fails host-allow-list validation will fail identically on every retry; per the step 6 AC's own reasoning ("retrying them just burns our attempt budget on something that will fail identically"), this should go straight to the DLQ, not consume `delivery_limit` retries with the production 30s default delay each. No test exercises this path through `handle_message` (`worker__test.py:292-301` only asserts `upload_job` raises, not what `handle_message` does with it). Fix: either give `CallbackUrlNotAllowedError` a `status_code`-like attribute that `_status_code_of` recognizes as non-retryable (e.g. treat it like a 4xx), or have `upload_job` raise/wrap it into something `decide_retry` classifies as non-retryable, and add a `handle_message`-level test asserting it lands on the DLQ on the first attempt.
2. `src/modules/audio/qwen_provider.py:52-68`, `src/modules/audio/gemini_provider.py:54-76` — REQUIREMENTS.md step 4 explicitly says "Stream the audio file into a temp file," but `synthesize()` calls a non-streaming `client.post(...)` and writes `response.content`, which httpx fully buffers in memory before any bytes reach disk. For a large `text` input driving a long audio file this defeats the purpose of "streaming" and holds the whole payload in memory. Fix: use `client.stream("POST", ...)` and iterate `response.aiter_bytes()` into the output file, per the AC's own wording.
3. No production process ever consumes `generateAudio` jobs: `docker compose up --build -d` (the documented local dev flow in `.github/CONTRIBUTING.md`'s "How to Start on Local Machine") only starts the `beatrice` GraphQL service, and `src/main.py` never touches the queue. A job published this way sits on the queue forever unless the developer separately remembers to run the worker by hand. **REQUIRED FIX — do not add a second, separate worker process or a second compose service for this.** The consumer must run *inside* the same process as the GraphQL API — i.e. `src/main.py`/`create_app` must start the `generateAudio` consumer itself (e.g. as a background task from a FastAPI lifespan hook) so one `beatrice` container/process serves GraphQL and drains the queue at the same time. `tests/conftest.py`'s `worker_container` fixture is unrelated to this finding — it is a test-only device (existed since step 5) that runs the consumer as an isolated Testcontainers process specifically so tests can control exactly when a message gets consumed; it says nothing about how the real app should be deployed and is not to be used as justification for a separate worker service.

## Test coverage

Coverage tracks CONTRIBUTING.md's tiers well: unit tests mock at the `httpx`/`aio_pika` boundary (no wiremock fixture used in unit tests), integration tests use Testcontainers + wiremock + MinIO for the real end-to-end paths (steps 3, 5, 6's DLQ path), and there are no evals for this module — correctly, since it has no LLM-driven natural-language output to score. The retry classification matrix in `retry__test.py` is thorough (4xx/408/429-with-and-without-Retry-After/5xx/network-error/`TtsProviderError`-with-and-without-status). The one meaningful gap is finding 1 above: `handle_message`'s branch for an upload-time `CallbackUrlNotAllowedError` has no test, and the existing test suite would not have caught the retryable-vs-DLQ misclassification. ADDRESS THIS.

## Nitpicks

- `worker.py:413-418` — a malformed message body (`json.loads`/`GenerateAudioJob.model_validate` failure) isn't wrapped in the same failure-handling path as synthesis/upload errors; it propagates out of `message.process()` and gets rejected-without-requeue by aio_pika's default behavior, with no structured log line and no DLQ entry. Probably fine in practice (only this codebase's own publisher writes to the queue), but if a poison message ever does show up, it disappears with no trace instead of anywhere inspectable. FIX THIS.
- `src/modules/audio/worker.py:238` — `_attempt_of` accepts `int | float | str` headers and casts via `int(...)`; a non-numeric string would raise `ValueError` uncaught (e.g. a hand-crafted `x-attempt: "abc"`), which would surface the same way as the malformed-message case above. Not exercised by tests, but low risk given only this codebase publishes to the queue. SKIP THIS. DO NOT ADDRESS IT.
